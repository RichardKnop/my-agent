# my-agent — an incident-investigation agent, built to learn the moving parts

This is a learning project, not a product. The goal is to hand-build every layer of a
tool-using LLM agent — no agent framework, no SDK — so each moving part is visible and you
can speak to it concretely from experience: context engineering, tool design, the agentic
loop, tracing, cost, and where it breaks.

This project implements a simple agent that investigates production incidents over logs, 
metrics and deploy history, and answers "why is production broken?".

## What it does

Ask it a question like:

```
go run ./cmd/agent "why did checkout error rate spike yesterday afternoon?"
```

and it will call a small set of read-only tools (`list_services`, `query_metrics`,
`query_logs`, `get_deploys`) against a mock observability dataset, reason across the
results over several turns, and produce a structured incident report:

```
Root cause: ...
Evidence: ...
Confidence: ...
Recommended action: ...
```

The mock dataset (`data/*.json`, generated by `scripts/gen_data.py`) simulates a real
cascading-failure incident: a deploy to `payments` at 14:31 UTC drops its DB connection
pool timeout too low, `payments` starts timing out, `checkout` (which calls `payments`
synchronously) sees its error rate and p99 latency spike, and that in turn shows up as 503s
in `frontend`. `inventory` / `inventory-db` are untouched — a control group, so the agent
has to actually localize the fault rather than assume every service is broken.

## Architecture

```
cmd/agent/main.go        CLI entrypoint: wires everything together, runs one question
internal/agent/          the agentic loop (call Claude -> run tools -> repeat) + system prompt
internal/claude/         thin, dependency-free Anthropic Messages API client (raw HTTP)
internal/tools/          tool implementations + their JSON-schema definitions
internal/data/           loads the mock dataset from data/*.json into memory
internal/trace/          appends one JSONL line per LLM call / tool call to traces/
data/                    the mock dataset (generated — see scripts/gen_data.py)
skills/                  placeholder for stage 2 (see Roadmap below)
```

Data flow for one question:

```
question
  -> agent.Investigate()
       -> claude.CreateMessage()         (send conversation + tool defs to Claude)
       -> Claude replies with tool_use   (or a final text answer)
       -> tools.Registry.Call()          (run the tool against internal/data.Store)
       -> tool_result appended to the conversation
       -> loop, until Claude stops asking for tools or MaxTurns is hit
  -> final text answer
```

Every LLM call and tool call is written to `traces/run-<timestamp>.jsonl` as it happens —
one JSON object per line, with latency and token usage. That file is the seed of stage 5
below (a real tracing/cost pipeline).

## Setup

Requires Go 1.27+ and Python 3 (only for the one-off data generator).

```
python3 scripts/gen_data.py     # writes data/*.json; the incident happens "yesterday" (UTC)
export ANTHROPIC_API_KEY=sk-ant-...
go run ./cmd/agent "why did checkout error rate spike yesterday afternoon?"
```

**Dates.** The generator places the incident on the day before you run it, so "yesterday
afternoon" is a meaningful question; re-run it if your data is a few days old. For a
reproducible dataset pin the day with `python3 scripts/gen_data.py --date 2026-08-23`, and
replay it with `-now 2026-08-24T09:00:00Z` so the agent's idea of "now" matches. The agent
is told the current time in its system prompt (`buildSystemPrompt` in `agent.go`) — without
it a model has no way to resolve "yesterday" and will guess a date from its training data.

Flags: `-model` (default `claude-sonnet-4-5-20250929`), `-max-turns` (default 8),
`-base-url`, `-timeout` (default 3m), `-now`, `-v` (default 1), `-data-dir`, `-trace-dir`. Run `go run ./cmd/agent -h`
for the full list.

### Running locally with Ollama (free, no API key)

The client speaks the raw Anthropic Messages API, and Ollama serves a compatible
`/v1/messages` endpoint, so the same agent runs against a local model with no code changes —
only a different base URL.

```
brew install ollama                          # or the Ollama.app from ollama.com
OLLAMA_CONTEXT_LENGTH=32768 ollama serve     # see the context-length note below
ollama pull qwen3-coder                      # ~19GB; 30B MoE, only ~3B active, fast on Apple Silicon
ollama list                                  # -model must match a name listed here

go run ./cmd/agent -base-url http://localhost:11434 -model qwen3-coder -timeout 10m \
  "why did checkout error rate spike yesterday afternoon?"
```

`-base-url` also defaults to `$ANTHROPIC_BASE_URL`, and the API key is only required when
the URL is Anthropic's own API.

Things that differ from running against Claude:

- **Context length.** Ollama's default context window is small, and through the
  Anthropic-compatible endpoint there's no request field to raise it. If the conversation
  (system prompt + tool definitions + up to 40 log lines per `query_logs` call) outgrows it,
  Ollama silently drops the oldest tokens and the agent "forgets" evidence or its
  instructions. Set `OLLAMA_CONTEXT_LENGTH` when starting the server (or the context-length
  setting in the Ollama app).
- **Smaller models investigate worse.** Expect more early stops, malformed tool arguments,
  ignored output format, or blaming the `inventory` control-group services. That's a
  feature for this project: running the same loop across models is a natural first step
  toward the evals stage. Lighter options if memory is tight: `qwen3:8b`, `qwen3:14b`.
- **Token counts are approximate** and there's no prompt caching, so the token numbers
  in traces don't map to cost the way they do for Claude.
- **Slower turns.** Each turn can take tens of seconds once the conversation grows, hence
  `-timeout 10m`.

Run the unit tests (no API key needed, nothing calls a real model). The tool tests run
the tools directly against the mock dataset. The agent-loop tests
(`internal/agent/agent_test.go`) replace the model with a scripted fake behind the
`agent.LLM` interface and assert on the conversation the loop sends back: tool_use →
tool_result pairing, error results, the turn cap:

```
go test ./...
```

## Design decisions worth being able to talk about

**Turn cap, not an unbounded loop.** `agent.Config.MaxTurns` (default 8) stops the loop if
Claude keeps calling tools without converging. In production this is the difference between
a bounded-cost request and a runaway one — every agent loop needs an explicit exit condition
beyond "the model decided to stop."

**`query_logs` truncates to 40 results and says so.** Returning every matching log line
would blow the context window on a noisy incident. The tool result includes
`total_matches` vs `returned` so Claude knows it's looking at a partial view and can narrow
the query — a small but real context-engineering decision, not an accident.

**The system prompt encodes a playbook, not just a persona** — it tells the agent the order
of investigation (services -> metrics -> deploys -> logs -> cross-service correlation) and
the exact output schema. That playbook living in one string in `agent.go` is the thing stage
2 (skills) below factors out into reusable, composable files.

**Retries with backoff on 429/5xx** (`internal/claude/client.go`), not on 4xx — the agent
should recover from a rate limit or a transient server error, not silently retry a malformed
request into an infinite loop.

**Tool definitions carry a `description` written for the model, not for a human reader** —
e.g. `query_logs`'s description tells Claude the result cap exists and what to do about it.
That's the same design problem as writing a good docstring, but the "reader" is the LLM
deciding whether and how to call the tool.

## Watching the loop

While it runs, the agent narrates every step of the loop on stderr (the final answer stays
on stdout), from `internal/agent/steplog.go`:

```
──── turn 2/8 ────
→ LLM request : 3 message(s) in conversation, 5.1 KB payload
← LLM response: 4.2s, stop_reason=tool_use, tokens in=1800 out=60
  model wants : query_logs({"service": "payments", "level": "ERROR", ...})  [id c2]
⚙ tool query_logs(...) → 8.4 KB result in 130µs
→ appended 1 tool_result block(s) as a new user message; looping back to the LLM
```

`-v 0` silences it, `-v 1` (default) shows each step, and `-v 2` also prints the full
system prompt, tool definitions and tool results — i.e. everything that actually enters the
model's context window. It also warns when the payload size and the reported input tokens
disagree badly, which usually means a local server truncated the context.

## Trace format

Each run writes `traces/run-<UTC timestamp>.jsonl`. Example lines:

```json
{"ts":"...","elapsed_ms":0,"event":"run_start","question":"...","model":"claude-sonnet-4-5-20250929"}
{"ts":"...","elapsed_ms":1420,"event":"llm_response","turn":1,"latency_ms":1420,"stop_reason":"tool_use","input_tokens":612,"output_tokens":98}
{"ts":"...","elapsed_ms":1421,"event":"tool_call","turn":1,"tool":"list_services","input":"{}","latency_ms":0,"is_error":false,"result_len":540}
{"ts":"...","elapsed_ms":9800,"event":"run_end","turns":4,"total_input_tokens":3100,"total_output_tokens":410}
```

This is deliberately the smallest possible version of agent observability. It's a flat file
today; the shape (a span per LLM/tool call, with duration and attributes) is exactly what
you'd emit as an OpenTelemetry span in stage 5.

## Roadmap (staged, one piece per session)

1. **Core agentic loop — done, this repo.** Tool-use loop, mock dataset, tracing, turn cap.
2. **Skills, not just prompts.** Move the playbook out of the system prompt into
   `skills/*.md` files (e.g. `high-error-rate.md`, `deploy-correlation.md`), with a
   `list_skills` / `load_skill` tool so the agent picks the right one instead of one prompt
   trying to cover every case.
3. **MCP server.** Expose `list_services` / `query_metrics` / `query_logs` / `get_deploys`
   as an MCP server instead of an in-process Go function registry, so any MCP client
   (Claude Desktop, another agent) can use them — this is the direct analogue of "build the
   MCP servers that let customers' agents read telemetry."
4. **Evals.** A fixed set of incident scenarios with known root causes; run the agent
   against each, score whether it identified the right cause, and track cost/latency per
   scenario over time — the harness that answers "does this still work after I changed the
   prompt/model/tools?"
5. **Tracing & cost as a real pipeline.** Replace the JSONL file with something queryable —
   ClickHouse is the obvious choice here — and build a small dashboard: cost per
   investigation, p99 agent latency, tool-call error rate.
6. **Real ClickHouse.** Swap `internal/data.Store` for a version backed by an actual
   ClickHouse instance (Docker + the ClickHouse OTel demo dataset), with the agent writing
   real SQL instead of calling fixed Go functions — text-to-SQL over telemetry, which is
   close to the actual `query_logs`/`query_metrics` a ClickStack customer would want.

## How this maps to what the job actually asks for

- *"Build agents that investigate incidents... use ClickStack as their substrate"* — this
  repo, with a real ClickHouse-backed data layer (stage 6) instead of mock JSON.
- *"Write skills, not just prompts"* — stage 2.
- *"Own the agent stack end-to-end: context engineering, tool design, evals, tracing, cost"*
  — tool result caps and turn caps are context engineering; `internal/tools` is tool design;
  stage 4 is evals; `internal/trace` is the seed of tracing; token counts in every trace
  line are the seed of cost tracking.
- *"Build the MCP servers... that let customers' agents read telemetry"* — stage 3.
- *"Latency, cost, context window limits, eval coverage, hallucinations on real telemetry"*
  — this is the exact list of problems the design decisions above (turn caps, result
  truncation, retries, evals) are pushing back against, at a small scale.
