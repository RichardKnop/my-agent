# my-agent — an incident-investigation agent, built to learn the moving parts

This is a learning project, not a product. The goal is to hand-build every layer of a
tool-using LLM agent — no agent framework, no SDK — so each moving part is visible and you
can speak to it concretely from experience: context engineering, tool design, the agentic
loop, tracing, cost, and where it breaks.

This project implements a simple agent that investigates production incidents over logs, 
metrics and deploy history, and answers "why is production broken?".

## What it does

Ask it a question like:

```
go run ./cmd/agent -now 2026-08-24T09:00:00Z "why did checkout error rate spike yesterday afternoon?"
```

(`-now` tells the agent what "now" is, so "yesterday" means the day of the incident in the
committed dataset; see **Dates** below.)

and it will call a small set of read-only tools (`list_services`, `query_metrics`,
`query_logs`, `get_deploys`) against a mock observability dataset, reason across the
results over several turns, and answer by submitting a structured incident report
through a `submit_report` tool, which the CLI prints as:

```
Root cause: ...
Root-cause service: ...
Triggering change: ...
Affected services: ...
Evidence:
  - ...
Confidence: ...
Recommended action: ...
```

The mock dataset (`data/*.json`, generated by `scripts/gen_data.py`) simulates a real
cascading-failure incident: a deploy to `payments` at 14:31 UTC drops its DB connection
pool timeout too low, `payments` starts timing out, `checkout` (which calls `payments`
synchronously) sees its error rate and p99 latency spike, and that in turn shows up as 503s
in `frontend`. `inventory` / `inventory-db` are untouched — a control group, so the agent
has to actually localize the fault rather than assume every service is broken.

## Architecture

```
cmd/agent/main.go        CLI entrypoint: wires everything together, runs one question
cmd/eval/main.go         eval CLI: runs the agent over every scenario in evals/, prints rates
internal/eval/           scenarios, grading, trace measurements, result summaries (stage 4)
evals/                   one directory per scenario (questions + expected answer), results/
internal/agent/          the agentic loop (call Claude -> run tools -> repeat) + system prompt
internal/claude/         thin, dependency-free Anthropic Messages API client (raw HTTP)
internal/tools/          tool implementations + their JSON-schema definitions
internal/data/           loads the mock dataset from data/*.json into memory
internal/trace/          appends one JSONL line per LLM call / tool call to traces/
data/                    the mock dataset (generated by scripts/gen_data.py, pinned to 2026-08-23)
skills/                  placeholder for stage 2 (see Roadmap below)
```

Data flow for one question:

```
question
  -> agent.Investigate()
       -> claude.CreateMessage()         (send conversation + tool defs to Claude)
       -> Claude replies with tool_use
       -> tools.Registry.Call()          (run the tool by name; handlers are bound to internal/data.Store)
       -> tool_result appended to the conversation
       -> loop, until Claude calls submit_report with a valid report or MaxTurns is hit
  -> agent.Report
```

Every LLM call and tool call is written to `traces/run-<timestamp>.jsonl` as it happens —
one JSON object per line, with latency and token usage. That file is the seed of stage 5
below (a real tracing/cost pipeline).

## Setup

Requires Go 1.27+. Python 3 is only needed to regenerate the dataset, which is committed.

```
export ANTHROPIC_API_KEY=sk-ant-...
go run ./cmd/agent -now 2026-08-24T09:00:00Z "why did checkout error rate spike yesterday afternoon?"
```

**Dates.** The committed dataset is pinned: the incident happens on **2026-08-23** (the
payments deploy lands at 14:31 UTC). Run the agent with `-now 2026-08-24T09:00:00Z`, the
morning after, so "yesterday afternoon" means the incident. Without `-now` the agent uses
the real current time, and "yesterday" points at a day with no data.

The agent is told the current time in its system prompt (`buildSystemPrompt` in
`agent.go`). Without it a model has no way to resolve "yesterday" and will guess a date
from its training data. Pinning the dataset, rather than regenerating it relative to
today, keeps runs reproducible: the same question sees the same data every time, which
is what makes runs (and later, evals) comparable across code, prompt and model changes.

`python3 scripts/gen_data.py` is seeded and reproduces the committed files exactly.
`--date YYYY-MM-DD` puts the same scenario on another day, and `--date yesterday` on
yesterday's date, so the agent works without `-now`. Don't commit data generated
with either.

Flags: `-now`, `-model` (default `claude-sonnet-5-5`), `-max-turns` (default 8, the turn
budget), `-max-tokens` (default 4096 per response; a response cut off at this limit fails
the run), `-base-url`, `-timeout` (default 3m), `-v` (default 1), `-data-dir`,
`-trace-dir`. Run `go run ./cmd/agent -h` for the full list.

### Running locally with Ollama (free, no API key)

The client speaks the raw Anthropic Messages API, and Ollama serves a compatible
`/v1/messages` endpoint, so the same agent runs against a local model with no code changes —
only a different base URL.

```
brew install ollama                          # or the Ollama.app from ollama.com
OLLAMA_CONTEXT_LENGTH=32768 ollama serve     # see the context-length note below
ollama pull qwen3-coder                      # ~19GB; 30B MoE, only ~3B active, fast on Apple Silicon
ollama list                                  # -model must match a name listed here

go run ./cmd/agent -base-url http://localhost:11434 -model qwen3-coder -timeout 10m \
  -now 2026-08-24T09:00:00Z "why did checkout error rate spike yesterday afternoon?"
```

`-base-url` also defaults to `$ANTHROPIC_BASE_URL`, and the API key is only required when
the URL is Anthropic's own API.

Things that differ from running against Claude:

- **Context length.** Ollama's default context window is small, and through the
  Anthropic-compatible endpoint there's no request field to raise it. If the conversation
  (system prompt + tool definitions + every tool result so far) outgrows it,
  Ollama silently drops the oldest tokens and the agent "forgets" evidence or its
  instructions. Set `OLLAMA_CONTEXT_LENGTH` when starting the server (or the context-length
  setting in the Ollama app).
- **Smaller models investigate worse.** Expect more early stops, malformed tool arguments,
  ignored output format, or blaming the `inventory` control-group services. That's a
  feature for this project: running the same loop across models is a natural first step
  toward the evals stage. Lighter options if memory is tight: `qwen3:8b`, `qwen3:14b`.
- **Token counts are approximate and split differently.** Ollama reuses the conversation
  prefix it processed on the previous turn, so `input_tokens` is only the newly appended
  part and the rest is reported as `cache_read_input_tokens`. The step log and traces show
  both. The numbers measure local compute, not cost.
- **Slower turns.** Each turn can take tens of seconds once the conversation grows, hence
  `-timeout 10m`.

Run the unit tests (no API key needed, nothing calls a real model). The tool tests run
the tools directly against the mock dataset. The agent-loop tests
(`internal/agent/agent_test.go`) replace the model with a scripted fake behind the
`agent.LLM` interface and assert on the conversation the loop sends back: tool_use →
tool_result pairing, error results, report validation, the turn budget and the forced
final report:

```
go test ./...
```

## Design decisions worth being able to talk about

**A turn budget the model knows about, not just a cap.** `agent.Config.MaxTurns`
(default 8) bounds the loop. In production this is the difference between a bounded-cost
request and a runaway one: every agent loop needs an explicit exit condition beyond "the
model decided to stop." But a cap the model doesn't know about just throws away work. A
thorough model keeps checking one more service until it's cut off, and the run fails
with nothing to show. So the budget is part of the context engineering:

- the system prompt states it ("at most 8 turns, on the last one only submit_report is
  allowed");
- the tool results before the final turn carry a note telling the model to submit its
  report now with the evidence it has;
- the final request sets `tool_choice` to force `submit_report`, which Anthropic enforces
  (Ollama accepts it but ignores it, so the note does the real work there).

A run that submits on the final turn is marked `budget_exhausted` in the trace: it
succeeded, but the investigation was cut short, which is worth tracking in evals. The
run fails only if the final turn produces anything other than a valid report.

**The answer is a tool call, not free text.** The model answers by calling
`submit_report`, whose input schema is the report (`summary`, `root_cause_service`,
`triggering_change`, `affected_services`, `evidence`, `confidence`, ...). Describing the
output as a tool's input is the standard way to get structured output from a
tool-calling model, and it's what makes evals possible without either brittle phrase
matching or a second model grading prose: `root_cause_service == "payments"` survives a
change of model or wording. `submit_report` lives in `internal/agent`, not the tool
registry, because it isn't a view of the system but part of the loop's protocol:

- a valid report ends the run (tools asked for in the same response are skipped);
- more than one `submit_report` call in a response is rejected as a whole, even if the
  reports are valid: every call gets the same error and the model resubmits, rather than
  the loop guessing which report was meant;
- an invalid report (e.g. `confidence: "very"`) goes back as an `is_error` tool_result,
  like any failing tool, and the model resubmits. The schema says the same thing, but
  servers such as Ollama don't enforce schemas, so the loop checks;
- a plain-text reply is not accepted as an answer: the loop replies with a reminder to
  use `submit_report`, which costs a turn. Models trained to "just answer" do this.

The field descriptions are prompt text, so they're written not to hint at the answer:
`triggering_change` and `root_cause_service` may be empty, so "no deploy did it" and "no
incident" stay expressible.

**`query_metrics` downsamples instead of deduplicating.** Every metric point is unique,
so grouping doesn't apply, but the model rarely needs 181 one-minute points to see
whether a series moved and when. Responses are capped at 30 points: longer windows are
averaged into equal-width buckets that keep both `avg` and `max` (an average alone
flattens a short spike), and the summary does the arithmetic (`median` as a baseline,
`max` and `max_at`). Narrowing the window gives full resolution: the same "overview,
then zoom" pattern as grouped logs. A 15-hour query went from ~7.9 KB to ~1.6 KB, and in
one local run the metrics calls had been ~11K of a 14K-token conversation and its
slowest turns. Buckets keep explicit timestamps rather than a compact "start + step +
array of values" encoding, because that would make the model count array positions to
work out times.

**`query_logs` groups repeated lines by default, then caps and says so.** Incident logs
are extremely repetitive: in the mock dataset 1,663 ERROR lines are just 3 distinct
messages. The first version returned the 40 newest raw lines, which over the incident
window meant 40 copies of the same error and *cut off the deploy line that caused the
incident*, as well as the moment the errors started. Now the default `grouped` mode
returns one row per (service, level, message) with `count`, `first_seen`, `last_seen` and
a few `sample_trace_ids`, ordered by `first_seen` so it reads as a timeline. For the
whole incident window across all services that's ~3 KB covering every line, versus
~8 KB of raw output covering 40 of them. `mode: "raw"` still returns individual lines
(newest first, capped at 40), and a `trace_id` filter lets the model take a sample trace
from a group and follow that one request across services. Both modes report totals and
`truncated`, so the model knows when it's seeing a partial view and should narrow the
query. Grouping is by exact message, which works because the mock messages are constant.
Real logs need templating first (masking IDs, durations and counters, e.g. the Drain
algorithm). That's a natural follow-up when the data layer moves to real ClickHouse.

**The system prompt encodes a playbook, not just a persona** — it tells the agent the order
of investigation (services -> metrics -> deploys -> logs -> cross-service correlation) and
when to submit the report. That playbook living in one string in `agent.go` is the thing stage
2 (skills) below factors out into reusable, composable files.

**Retries with backoff on 429/5xx** (`internal/claude/client.go`), not on 4xx — the agent
should recover from a rate limit or a transient server error, not silently retry a malformed
request into an infinite loop.

**Tool definitions carry a `description` written for the model, not for a human reader** —
e.g. `query_logs`'s description explains grouped vs raw output, the result caps, and how
to follow a sample trace_id across services.
That's the same design problem as writing a good docstring, but the "reader" is the LLM
deciding whether and how to call the tool.

## Watching the loop

While it runs, the agent narrates every step of the loop on stderr (the final report goes
to stdout), from `internal/agent/steplog.go`:

```
──── turn 2/8 ────
→ LLM request : 3 message(s) in conversation, 5.1 KB payload
← LLM response: 4.2s, stop_reason=tool_use, tokens in=1800 out=60
  model wants : query_logs({"service": "payments", "level": "ERROR", ...})  [id c2]
⚙ tool query_logs(...) → 8.4 KB result in 130µs
→ appended 1 tool_result block(s) as a new user message; looping back to the LLM
```

`-v 0` silences it, `-v 1` (default) shows each step, and `-v 2` also prints the full
system prompt, tool definitions and tool results — i.e. everything that actually enters the
model's context window. It also warns when the payload size and the reported prompt
tokens (`input_tokens` plus cached tokens) disagree badly, which usually means a local
server truncated the context.

## Trace format

Each run writes `traces/run-<UTC timestamp>.jsonl`. Example lines:

```json
{"ts":"...","elapsed_ms":0,"event":"run_start","question":"...","model":"claude-sonnet-5-5"}
{"ts":"...","elapsed_ms":1420,"event":"llm_response","turn":1,"latency_ms":1420,"stop_reason":"tool_use","input_tokens":612,"cache_read_input_tokens":0,"output_tokens":98}
{"ts":"...","elapsed_ms":1421,"event":"tool_call","turn":1,"tool":"list_services","input":"{}","latency_ms":0,"is_error":false,"result_len":540}
{"ts":"...","elapsed_ms":9790,"event":"tool_call","turn":4,"tool":"submit_report","input":"{\"summary\":...}","latency_ms":0,"is_error":false}
{"ts":"...","elapsed_ms":9800,"event":"run_end","turns":4,"total_input_tokens":3100,"total_cache_read_input_tokens":0,"total_output_tokens":410,"budget_exhausted":false,"report":{"summary":"...","root_cause_service":"...",...}}
```

`submit_report` calls are traced as `tool_call` events like any other tool; a rejected
report has `is_error: true` and an `error` field saying what was wrong. Every run ends with
exactly one `run_end` line, however it ends. A successful run's `run_end` carries the
submitted `report`. A failed run (model API error, turn cap, no valid report on the final
turn) gets the same line with an `error` field instead, and a failed model call also
logs an `llm_error` event for its turn:

```json
{"ts":"...","elapsed_ms":4100,"event":"llm_error","turn":3,"latency_ms":2050,"error":"messages api error (status 500): ..."}
{"ts":"...","elapsed_ms":4100,"event":"run_end","turns":3,"total_input_tokens":2400,"total_cache_read_input_tokens":0,"total_output_tokens":160,"budget_exhausted":false,"error":"turn 3: messages api error (status 500): ..."}
```

This is deliberately the smallest possible version of agent observability. It's a flat file
today; the shape (a span per LLM/tool call, with duration and attributes) is exactly what
you'd emit as an OpenTelemetry span in stage 5.

## Evals

`go run ./cmd/eval` runs the agent over a set of incident scenarios with known answers and
reports how often it finds the root cause, and at what cost:

```
go run ./cmd/eval -base-url http://localhost:11434 -model qwen3-coder   # free, local
go run ./cmd/eval -repeat 3 -run payments                               # Anthropic: costs money
```

Each scenario is a directory under `evals/` with a `scenario.json`: the dataset to use, the
time the agent is told it is, several phrasings of the question, and the expected answer.
Every question is a full, independent agent run (asked `-repeat` times), and each run is:

- **graded on its structured report**, with no phrase matching and no grader model.
  `root_cause_service` must equal the expected service, and `triggering_change` must
  *contain* the expected identifier, because models phrase it freely ("v2.14.0",
  "payments deploy v2.14.0"). Those two decide pass/fail. `affected_services` is scored
  as the share of expected services named (missing a downstream service is a weaker
  answer, not a wrong one), and naming a healthy control service is recorded separately;
- **measured from its trace**: turns, tokens, duration, tool calls and tool errors,
  rejected reports, and whether the budget ran out. A change that keeps the pass rate but
  doubles the turns is still a regression, and reading the trace (rather than the agent's
  internal counters) means evals depend only on the record a production pipeline would see.

Output is one line per run while it goes, then a summary table per scenario. The first
run against qwen3-coder:

```
[1/6] payments-pool-timeout q0 r1  PASS  service="payments" change="payments v2.14.0" affected=67%  turns=7 rejected=0 43s
...
[5/6] payments-pool-timeout q4 r1  FAIL  service="inventory" change="None identified; performance degradation occurred without an apparent deploy." affected=33%  turns=8 rejected=0 26s
[6/6] payments-pool-timeout q5 r1  PASS  service="payments" change="payments service deploy v2.14.0" affected=100%  turns=8 rejected=0 35s

               scenario  pass  root cause  change  affected  errors  budget out  rejected  tool errs  turns  tokens in/cached/out  time
  payments-pool-timeout   5/6         5/6     5/6       78%       0           4         0          0    7.7        4.7K/30.7K/923   34s
```

The failure is the leading question, "Did the inventory service cause the checkout
errors yesterday?". The agent investigated only inventory, found no errors and no deploy
there, and still answered "inventory" with high confidence, without ever looking at
payments. That's confirmation bias, and it only shows up because one phrasing points at
the wrong service.

The full results (every report, grade and measurement, plus the model, settings and git
commit) go to `evals/results/<timestamp>-<model>.json`, small enough to commit, so a
prompt or model change can be compared against an earlier run. Each run's trace is kept
under `traces/eval-<timestamp>/`. Two design points:

- **Variety comes from phrasings, not repetition.** A local model asked the same question
  twice often makes nearly the same run, so each scenario asks the question several
  ways: vague, specific, from the user's side ("503s on the website"), and one that
  points at the wrong service ("did inventory cause it?").
- **Infrastructure failures aren't agent failures.** The client already retries 429s and
  5xx, so if a model call still fails, the eval stops instead of recording every
  remaining run as a wrong answer.

There's one scenario so far, on the committed dataset. More scenarios need their own
datasets from the generator: a deploy that isn't the cause, an incident with no deploy, a
quiet day with nothing wrong. Those keep the prompt from being tuned to one incident.

## Roadmap (staged, one piece per session)

1. **Core agentic loop — done, this repo.** Tool-use loop, mock dataset, tracing, turn cap.
2. **Skills, not just prompts.** Move the playbook out of the system prompt into
   `skills/*.md` files (e.g. `high-error-rate.md`, `deploy-correlation.md`), with a
   `list_skills` / `load_skill` tool so the agent picks the right one instead of one prompt
   trying to cover every case.
3. **MCP server.** Expose `list_services` / `query_metrics` / `query_logs` / `get_deploys`
   as an MCP server instead of an in-process Go function registry, so any MCP client
   (Claude Desktop, another agent) can use them — this is the direct analogue of "build the
   MCP servers that let customers' agents read telemetry."
4. **Evals — started.** A fixed set of incident scenarios with known root causes; run the
   agent against each, score whether it identified the right cause, and track cost/latency
   per scenario over time — the harness that answers "does this still work after I changed
   the prompt/model/tools?" The runner and the first scenario exist (see **Evals** above);
   next are more scenarios from the generator, a sampling temperature for repeat runs, and
   a grader model for the free-text summary.
5. **Tracing & cost as a real pipeline.** Replace the JSONL file with something queryable —
   ClickHouse is the obvious choice here — and build a small dashboard: cost per
   investigation, p99 agent latency, tool-call error rate.
6. **Real ClickHouse.** Swap `internal/data.Store` for a version backed by an actual
   ClickHouse instance (Docker + the ClickHouse OTel demo dataset), with the agent writing
   real SQL instead of calling fixed Go functions — text-to-SQL over telemetry, which is
   close to the actual `query_logs`/`query_metrics` a ClickStack customer would want.

## How this maps to what the job actually asks for

- *"Build agents that investigate incidents... use ClickStack as their substrate"* — this
  repo, with a real ClickHouse-backed data layer (stage 6) instead of mock JSON.
- *"Write skills, not just prompts"* — stage 2.
- *"Own the agent stack end-to-end: context engineering, tool design, evals, tracing, cost"*
  — tool result caps and turn caps are context engineering; `internal/tools` is tool design;
  stage 4 is evals; `internal/trace` is the seed of tracing; token counts in every trace
  line are the seed of cost tracking.
- *"Build the MCP servers... that let customers' agents read telemetry"* — stage 3.
- *"Latency, cost, context window limits, eval coverage, hallucinations on real telemetry"*
  — this is the exact list of problems the design decisions above (turn caps, result
  truncation, retries, evals) are pushing back against, at a small scale.
